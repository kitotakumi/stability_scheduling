## 3. 考察

### 3.1 GAの「第0世代で最良解到達」問題 — 最大の論点

**観測事実**: weights=[1.0, 0.0]において、GAの最良解到達世代が**全10試行で第0世代（evaluations=50）**であった。つまり初期集団の50個体を評価した時点で、残り500世代の進化が一切メイクスパンを改善できていない。

**原因分析**:

1. **アクティブスケジュール生成（GT法デコード）の威力**: GAの遺伝子はジョブ番号の順列であり、`get_gantt_reactive` で「左詰め挿入」（アクティブスケジュール）にデコードされる。アクティブスケジュールは最適解を含む空間だが、**ランダム順列からでも非常に良質な解が生成される**性質を持つ。MT10のようなベンチマーク問題では、50個のランダムアクティブスケジュールの中に既にかなり良い解が含まれることは十分あり得る。

2. **遺伝子型-表現型のマッピングの多対一性**: GT法デコードでは、異なる遺伝子が同一のスケジュールにデコードされる（多対一マッピング）。交叉・突然変異で遺伝子を変えても表現型（スケジュール）が変わらない、あるいは悪化するケースが多く、**探索が実質的に停滞**する。

3. **リスケジューリング問題の特殊性**: 全工程ではなく、リスケ対象工程のみが探索対象。探索空間が通常のJSSPより小さく、ランダムでも良い解が当たりやすい。

4. **シード固定との関連**: 他のAIの指摘にあった「seedsを固定しているから」という指摘は、**weight_sweepの結果に関しては正しい**。weight_sweepではseed=42を固定して全重みで同じランダム系列を使うため、GAのメイクスパンが全重みで1080（初期解と同じ）になっている。しかし10回比較実験では試行ごとにシードを変えており（7, 107, 207,...）、そちらの結果は有効。**weight_sweepでGAが全く改善しないのは、seed=42かつ200世代では初期解を超えられなかった1特定の初期集団に依存している**。

**結論**: GAの第0世代収束は、アクティブスケジュール生成の性質上自然な現象であり、バグではない。ただし、500世代×50個体＝25,000回以上の評価が改善に全く寄与していないことは、**計算資源の大幅な無駄**を意味する。

### 3.2 各手法の強みと弱み

**GA**:
- 改善成功率が高い（効率性のみで100%）
- 最良解到達が極めて高速（0.2秒、50評価）
- しかし残りの80秒（25,000+評価）は完全に無駄
- 安定性は最も悪い（weights=[1.0,0.0]で平均9.73）

**ILS(insert)**:
- 効率性のみ条件で**最良のメイクスパン**（平均1047.5, 最良1044）
- 改善成功率100%（効率性のみ条件）
- N5近傍 + insert摂動の組み合わせが効果的
- CPU時間は中程度（平均23秒）

**ILS(swap)**:
- CPU時間が最も短い（平均12秒）
- 安定性重みを入れると改善成功率が大幅低下（50%）
- N5近傍のswap摂動だけでは探索の多様性が不足

### 3.3 安定性重み付加時の挙動

weights=[0.9, 0.1]にすると全手法で改善成功率が低下。特にILS(swap)は50%、ILS(insert)は60%に落ちる。これは:

- 安定性を考慮すると、メイクスパンを改善する操作順序変更にペナルティがかかる
- ILSでは初期解からの変更が少ないほど安定性が高いため、**局所探索が初期解から動けなくなる**
- ILSのMakespan=1080の試行を見ると、BestEvals=6（初期局所探索のみ）で止まっている → 初期局所探索で改善方向が見つからなかった

### 3.4 weight_sweepの問題点

**GAが全重みでMakespan=1080**: seed=42の1回だけの試行であり、かつ200世代と少ないため、統計的意味がない。10回比較実験では1046まで改善できているので、これはサンプリングの問題。

**ILS(swap)も全重みでMakespan=1080**: 同様にseed=42の1試行。ILS(swap)のstability=0.00 (全重み) は、初期解から一切動かなかったことを示唆。

**改善案**: weight_sweepでも複数シード（最低5個）の平均を取るべき。

## 4. コード改善提案

### 4.1 GAの早期終了・適応的世代数

GAは第0世代で収束する傾向が強い。改善なし世代が一定数続いたら打ち切る early stopping を実装すべき。

```python
# 例: 50世代改善なしで終了
if gen - best_gen > 50:
    break
```

これにより計算時間を80秒→数秒に削減できる。

### 4.2 GAの集団多様性維持

第0世代で最良解に到達してしまう根本原因はアクティブスケジュールデコードだが、以下で改善の余地がある:

- **集団サイズの増加**: 50→100-200にして初期集団の品質を上げる（ただし第0世代収束問題を悪化させる可能性も）
- **突然変異率の引き上げ**: 0.1は低すぎる。0.2-0.3で多様性を維持
- **ニッチング/クラウディング**: 集団内の多様性を明示的に維持する選択圧

### 4.3 weight_sweepの統計的改善

```python
# 複数シードで平均を取る
SWEEP_SEEDS = [7, 42, 107, 207, 307]
for seed in SWEEP_SEEDS:
    # 各重みで実行して平均を取る
```

### 4.4 ILSの安定性重み時の改善

安定性を考慮する場合にILSの改善成功率が低いのは、初期局所探索が初期解（変更なし＝安定性最良）から動けないことが原因。対策:

- **初期解に弱い摂動を加えてから局所探索を開始**: 安定性ペナルティを超えてメイクスパンを改善する「きっかけ」を与える
- **焼きなまし的な受理基準**: 現在は厳密に改善した場合のみ受理だが、SA的に悪化も確率的に受理すると探索空間を広げられる

### 4.5 GAとILSの解表現の統一

現在、GAはジョブ順列（GT法デコード→アクティブスケジュール）、ILSは機械内操作順序（semi-activeスケジュール）と異なる解表現を使用している。公平な比較のためには:

- **ILSもアクティブスケジュール生成を使う**: ILSのbuild_ganttでも左詰め挿入を行えば、より良いメイクスパンが期待できる
- または**GAもsemi-activeデコードを使う**: ただしこれはGAの性能を下げる可能性が高い

### 4.6 正規化パラメータの問題

GAとILSで正規化パラメータの推定方法が異なる:
- GA: 集団から推定（世代ごとに更新）
- ILS: 事前にランダムサンプリング+局所探索で推定

重みを変えて比較する際、正規化の違いが目的関数値の比較を困難にしている。**共通の正規化パラメータを事前計算で決定すべき**。

### 4.7 評価回数ベースの公平な比較

現在の実験は「GA 500世代, ILS 800反復」と固定だが、評価回数が大きく異なる:
- GA: 平均25,499評価
- ILS(swap): 平均14,922-15,391評価
- ILS(insert): 平均36,068-38,216評価

**同一評価回数（例: 20,000回）で打ち切る実験設計**がより公平。

## 5. 理論的考察

### 5.1 アクティブスケジュールとメイクスパン最適性

Giffler-Thompson (GT) アルゴリズムによるアクティブスケジュール生成は、最適解がアクティブスケジュールの集合に必ず含まれることが保証されている（定理: 最適スケジュールは必ずアクティブスケジュール）。ランダムな優先順位でGT法を適用すると、比較的少数のサンプルで良質な解が得られる。

MT10の既知最適解は930（通常JSSP）。リスケジューリング問題では確定済み部分がある分、探索空間が縮小されるため、ランダムでも良い解が当たりやすい。

### 5.2 N5近傍の理論的背景

Nowicki & Smutnicki (1996) のN5近傍は、クリティカルブロックの境界交換のみを行うため、閉路が生じないことが保証されている。ILS+N5は JSP のメタヒューリスティクスとして定評があり、ILS(insert)の1044という結果は妥当。

### 5.3 安定性指標の設計

現在の安定性指標 `Σ |init_pos - current_pos| / (current_pos + 1)^1.25` は:
- 先頭付近の順位変更に大きなペナルティを課す（position weighting）
- しかし `current_pos` で重み付けしているため、**改善によって先頭に来た操作ほどペナルティが大きい**という逆インセンティブがある
- `init_pos` ベースの重み付けの方が直感的かもしれない（元々先頭だった操作が後ろに回ることを重くペナルティ）
