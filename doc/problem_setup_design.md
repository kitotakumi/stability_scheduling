## 1. 設計方針

本研究の核心は「探索構造のミクロ分析」であり、再現性と因果分析の精度を最優先する。

### 1.1 外乱注入の2系統と本研究の立場

| 系統 | 代表研究 | 外乱の与え方 | 「大小」の作り方 |
|---|---|---|---|
| シミュレーションベース | Zhang, Gao & Li (2013) | ホライズン上に Poisson 到着・指数故障を**ストリーム**生成、周期＋イベント駆動で反復リスケ | 到着率 λ・新ジョブ数・故障レベル Ag |
| **固定イベントベース** | Kundakcı & Kulak (2016) | 決まった外乱を固定時刻に与え、単一/少数のリスケ点で評価 | 問題規模（op数） |

本研究は**ミクロ分析**なのでストリームの確率揺らぎを避け、**固定イベントベース**を採る。
- **単一リスケジューリングポイント**（外乱イベント1個）
- 外乱は**作業遅延のみ**（routing 固定のまま順序調整で対処）
- シナリオ固定で再現性を担保

### 1.2 二目的（効率・安定性）

- **効率** ＝ makespan。
- **安定性** ＝ $S_p$ からの**順列偏差（重みなし, β=0）**: 各機械ごとに `Σ |init_pos − cur_pos|` を合計。
  - 卒論では β=1.25 の重み付き偏差だったが、修論では **β=0（重みなし）** に変更。理由: makespan と直交し、近傍演算子（順序の入れ替え）と整合的なため。pilot で β=0 でも memetic+PR > LS の HV 優位（large）・フロント非潰れを確認済み。
- 重み掃引でパレートフロントを描く。

## 2. 難易度軸 ＝ 外乱の「位置」【本研究の中核】

難易度（＝アルゴリズムが差を出せる土俵）の指標は **headroom**:

> **headroom ＝ `RSR_makespan − 最適化後makespan`**（元順序のまま右シフトする RSR に対し、順序を並べ替えてどれだけ makespan を縮められるか）

- `headroom = 0` → 右シフトが既に最適、全手法が同じ解 → **縮退（区別不能）**
- `headroom 大` → 並べ替えに価値、良い手法ほど縮める → **手法間の差が出る**

### 2.1 難易度を作るレバーの比較（実測結論）

| レバー | headroom の差 | 採否 |
|---|---|---|
| 遅延量 δ | 出ない（δ に不変。§3） | ✗ |
| 問題セット | ほぼ一定（~25。mt10:29/la21:24/la36:26） | △ 一般性用。難易度軸にはならない |
| **外乱の位置** | **大きく動く**（早→大／遅→小） | ✅ **採用** |

外乱の**位置**は「スケジュールのどれだけを再最適化するか（reschedule horizon）」を決める:

- **早い外乱** → 再スケ範囲 大 → 最適解が $S_p$ から**遠い** → headroom 大 → ILS の近傍前提が崩れ Memetic/PR が有利になりうる
- **遅い外乱** → 再スケ範囲 小 → $S_p$ **近傍** → headroom 小 → ILS で十分

これは当初の仮説「外乱小→$S_p$近傍→ILS有利／外乱大→遠い→Memetic・PR有利」を、**遅延量の代わりに"位置"で忠実に実装**したもの。位置は問題規模と違い「**同じ問題の中で**」難易度を振れる（問題規模では不可能）。

### 2.2 実測：位置は horizon を綺麗に制御するが headroom は op 依存（la36, GA S_p, MS=1580）

| pos | reschedule horizon | headroom |
|---|---|---|
| 0.00 | 198 | 59 |
| 0.17 | 164 | **62** ← 大の候補 |
| 0.26 | 142 | **0（縮退）** |
| 0.40 | 114 | **0（縮退）** |
| 0.52 | 75 | 64 |
| 0.72 | 29 | **29** ← 小の候補 |
| 0.78 | 14 | **0（縮退）** |
| 0.87 | 3 | 0（縮退） |

- **reschedule horizon は位置に綺麗に比例**（早 198 → 遅 3）＝「近傍/遠い」は位置で確実に制御できる。
- **headroom は位置に綺麗には比例しない**（0〜64でガタガタ。同じ大horizonでも 0.26/0.40 は縮退）。headroom は op ごとの局所競合構造に依存する。
- ∴ **位置を決めた上で `measure_headroom` で headroom>0 の op を選ぶ**（機械的に位置だけで選ぶと縮退を引く）。

### 2.3 reschedule_time の定義（重要・2026-06 修正）

`reschedule_time = 遅延op の right-shift 後の終了時刻`（**+1 しない**）。[gantt_chart_operation.py](../gantt_chart_operation.py) で `latest_end + 1` → `latest_end` に修正済み。

- 遅延opの**直後工程**は「遅延op終了」ちょうどに開始する。+1 すると `start < reschedule_time` 判定でこの直後工程まで凍結され、**外乱に直撃された一番リスケすべき工程**を最適化対象から外してしまう。これが mt10 を headroom 0 の縮退に見せていた原因（5/26 の複数遅延書換 commit 201b7b0 で混入したリグレッション、6/3 修正）。
- **現実妥当性**: 「遅延が解消する時刻に再スケ。実際に走った作業は凍結、ブロックされて始められなかった直後工程はリスケ」。検知時刻（遅延opの"元"終了）まで戻すのは却下＝遅延中も動く他機械の独立op（実走済み）までリスケ対象化して非現実的。
- 修正後: **mt10_delay60 headroom 0→29**（pipeline でも 1050 確認）。la21=24/la36=26 は不変。

## 3. 背景: なぜ遅延量・複数遅延・故障では難易度を作れないか（撤回理由）

### 3.1 δ も遅延箇所数も headroom を動かさない（実測）

| シナリオ | 外乱 | headroom |
|---|---|---|
| mt10 delay60 → delay90 | 単一δ +50% | 29 → 29（不変） |
| la36 単一 → multi3 → multi5 | +120 → +242 | 26 → 26 → 26（不変） |

### 3.2 理論

クリティカル路の遅延は再スケ問題に「**全体を一定量だけ右にずらす**」効果しか持たない（定数の right-shift オフセット）。RSR も最適解も同じ δ を吸収するので差＝headroom は δ に不変。「時間軸で $S_p$ から遠い」と「順序空間で最適解が遠い」が単純遅延では**デカップル**する。複数遅延も臨界路上では一様シフトの重ね合わせで同じ。**非フレキシブルJSPでは作業遅延と機械故障は同一ファミリー**（別機械に逃がせず「待つ＋並べ替える」のみ）なので故障時間を振っても同結論。

### 3.3 文献的裏付け

- **Zhang (2013)** は外乱大小を**到着率・新ジョブ数**（ストリーム前提）で作る。「単一遅延を何分にするか」ではない。
- **Kundakcı (2016)** は外乱大小を独立変数化せず、**問題規模**をスケール軸にする。

本研究は単一遅延の「大きさ」で難易度を作らない点で先行研究と整合する。難易度は**位置**で作る（§2）。

## 5. 外乱設計（ゼロから再定義）

| 要素 | 定義 | 根拠 |
|---|---|---|
| **遅延量** | 対象op の **PT × 1.0**（処理時間を倍に）。全シナリオ共通の固定量 | slack を超えてリスケを誘発する最小限で十分。**headroom は δ 不変**なので大きくする意味はない |
| **位置（難易度軸, 大小2水準）** | la36 で **大≈0.17**（horizon 164 / headroom 62）と **小≈0.72**（horizon 29 / headroom 29）。一般性3問題＋大規模は中間位置に単一外乱 | reschedule horizon を制御＝近傍/遠い |
| **対象op** | 各位置近傍のクリティカルop のうち **headroom>0 を `measure_headroom` で確認して選ぶ** | 位置だけだと縮退op を引く（§2.2）。cherry-pick ではなく非縮退の確認 |
| **$S_p$（初期スケジュール）** | **GA 500世代（最適化しすぎない）**。Memetic は使わない | 締めすぎると再スケ余地が減る。適度に甘い予測スケジュールが現実的＆ headroom を残す。Memetic は最適寄りで余地を潰すため不可 |
| **reschedule_time** | 遅延op終了（+1なし、§2.3） | 直後工程を正しくリスケ対象に |

> la36 の大小2点は §2.2 の実測で選定済み（大=0.17 / 小=0.72）。他シナリオも作成後 `measure_headroom` で非縮退（headroom>0）を必ず確認。

## 6. headroom 診断ツール

`tools/measure_headroom.py`（RSR比で headroom を測る）:
- `--scenario NAME` … 既存シナリオの headroom を測る
- `--scan NAME` … initial_gantt の全クリティカルopをターゲットに振り headroom 分布を出す

用途: ①各シナリオの非縮退確認、②la36 の位置→headroom の校正（大小2点の選定, §2.2）、③（任意）ILS最適解と $S_p$ の順序距離測定。
